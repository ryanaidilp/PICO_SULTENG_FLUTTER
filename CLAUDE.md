# Pico - Flutter Monorepo

This is a Flutter monorepo generated by Archipelago. All patterns are validated and production-ready.

## Workspace Structure

```
pico/
  apps/                    # Host applications
    pico/          # Main app - orchestrator, no business logic
  shared/                  # Cross-cutting shared packages
    consent_api/           # Telemetry consent gate + PII scrubbing contracts
    consent_impl/          # Persisted gate, default scrub rules, debug override
    dependencies/          # Centralized dependency re-exports (GetIt, injectable, auto_route, slang, state management)
    dependencies_core/     # Flutter-free half of dependencies (equatable, get_it, injectable, meta)
    feature_sdk/           # Base FeatureSDK contract + FeatureSDKRegistry
    locale_core/           # i18n/l10n setup
    router_registry/       # Route registration abstraction
  features/                # Feature modules
  infrastructure/          # SDK wrappers and vendor implementations
  packages/                # App-specific packages
  utilities/               # Generic utilities
  devtools/                # Development tooling
```

## Architecture Patterns

### API/Impl Split

Used when a capability is consumed by multiple packages or needs vendor swapping. The `_api` package defines contracts (abstract classes), and `_impl` packages provide concrete implementations.

### Impl + Noop (build_prepare swap)

For debug-only tooling that must not ship in the **production flavor** (app_debugger and its sub-tools, the Blackbox recorder and its native plugins). `build_prepare.yaml` at workspace root defines the swaps. The build's flavor decides: flavors in `internal_flavors` (default `development`, `staging`, `alpha`, `beta`) keep the tools, including in release mode, so QA builds have the debugger. Every other flavor gets the noop twins. Monitoring and the launch tracker are **not** swapped: they ship in every flavor, gated by consent.

A second list, `debug_build_only`, follows the build **mode** instead: `build-prepare --mode release|profile` swaps it to the noop twins for every flavor, internal ones included, and `--mode debug` restores it. It holds Marionette (`app_marionette` -> `app_marionette_noop`), so no release or profile build contains it.

The Fastfile runs `build-prepare --flavor <flavor> --mode release` before every build, `build-prepare --check-leaks --flavor <flavor> --mode release` after it, and `build-prepare --restore` at the end. By hand: `melos run build-prepare:production` (alias `build-prepare:release`), then `melos run build-prepare:debug`. Never run the production swap before an internal build.

### Driving the running app (Marionette MCP)

Debug builds install LeanCode Marionette's `MarionetteBinding` (`features/app_marionette`, called as `ensureAppBinding(...)` first in `bootstrap.dart`), so an agent can read the widget tree, tap, enter text, scroll, take screenshots and read logs. Release and profile builds swap it out (above).

1. Once per machine: `dart pub global activate marionette_mcp`. The project's `.mcp.json` registers the server for Claude Code (or run `claude mcp add --transport stdio marionette -- marionette_mcp`).
2. Run the app in **debug**: `cd apps/pico && flutter run --flavor development -t lib/main_development.dart`.
3. Copy the VM service URI it prints (`ws://127.0.0.1:<port>/<token>=/ws`) and call the `connect` tool with it.
4. Use `get_interactive_elements`, then `tap`, `enter_text`, `scroll_to`, `take_screenshots`, `get_logs`. Match widgets by `ValueKey<String>` when text is ambiguous.

Under `flutter test` and in integration or Patrol tests the plain binding is used. UI kit controls (`PicoButton`, `PicoTextField`, ...) are reported through `isUiKitInteractive` in the kit; add a new interactive kit control there. Never call `WidgetsFlutterBinding.ensureInitialized()` or another binding before `ensureAppBinding`.

### Dual-GetIt (Global + Local scopes)

- **Global scope**: SDKs, infrastructure (network, monitoring, analytics) - registered as eager/lazy singletons
- **Container per feature**: repos, datasources, usecases live in the feature's `FeatureContainer`, a child GetIt that never falls back to the root; `<name>_imports.dart` forwards each root type the feature uses

### Feature manifest + lazy SDK

Each feature's global module registers a const `FeatureManifest` (routes, page configs, optional initial-path claim) in `FeatureSDKRegistry`, and its SDK as a lazy singleton behind the feature's `_api` port. The host reads the manifests during pre-launch, so the route table is complete at boot while a feature nobody opens is never built. A manifest never resolves from GetIt in its constructor, `isEnabled` or `registerRoutes`. Only a feature that must exist before the first frame (auth's session restore, debug tooling) implements `FeatureSDK` (a manifest plus `launch()`) and is registered eagerly.

**Guard tests:** `apps/pico/test/di/lazy_feature_sdk_test.dart` fails when `initializeInjector()` builds a `*SDKImpl` that is not in its commented `_eagerByDesign` allowlist, or a manifest is an unlisted `FeatureSDK`. `base_scope_budget_test.dart` snapshots the instances built at boot (`flutter test --update-goldens` accepts a change), `port_singleton_test.dart` checks that `// di-global:` ports are singletons and that `*_imports.dart` files only forward, and `test/architecture/feature_boundary_test.dart` forbids depending on another feature's `_impl`. Each feature's `test/di/<name>_di_test.dart` builds its container from a fake root holding only the imported types and checks the teardown.

### Two-Phase Initialization

1. **Pre-launch (blocking)**: DI setup, route registration, critical SDKs
2. **Post-launch (non-blocking)**: Analytics, feature flags, remote config

### Telemetry Consent + PII Scrubbing

Every outbound telemetry payload passes one choke point. `shared/consent_api`
owns the contracts (`ConsentPurpose`, `ConsentState`, `ConsentGate`,
`TelemetryScrubber`, `ScrubRules`); `shared/consent_impl` owns the persisted
gate, the default rule set and the debug override.

- **Fail closed.** Every purpose is denied until your app records a decision.
  `ConsentInitializer.initialize(GetIt.I)` runs in **pre-launch**, before
  `initializeInjector()` — a gate installed after the first tracked event does
  not gate that event.
- **Four independent purposes**: `analytics`, `diagnostics`, `marketing`,
  `targeting`. A user may lawfully accept one and refuse another, so never
  collapse them into a single boolean. Wire your consent sheet to
  `getIt<ConsentGate>().recordAll({...})`.
- **Analytics**: consent and scrubbing interceptors are always first in the
  chain, ahead of anything in `AnalyticInterceptorRegistry`. Suppression covers
  `setUserId`/`setUserProperty`/`setUserProperties`/`registerSuperProperties`
  as well as `track`.
- **Monitoring**: `ConsentAwareMonitoring` holds the `AppMonitoring` DI binding
  and wraps `MonitoringFanoutImpl`. Never register the fanout as
  `AppMonitoring` — that bypasses the gate.
- **Feature flags**: `EvaluationContext.toMap()` omits `email` unless
  `ConsentPurpose.targeting` is granted.
- **Author-time**: the `no_pii_in_telemetry` lint flags deny-listed keys in map
  literals passed to `track`, `log`, `breadcrumb` and `recordError`.
- **QA**: telemetry is silent until consent is recorded. Use
  `--dart-define=CONSENT_DEBUG_GRANT_ALL=true` (debug builds only).

Never "fix" a silent-telemetry report by seeding a granted state in production
code — that turns the fail-closed gate into a fail-open one.

### Locale persistence

slang's `LocaleSettings` is **in-memory only** — it mutates a plain in-process
singleton, so a locale set through it is gone the moment the process dies.
`shared/locale_core` owns both halves of making the choice durable:

| Concern | Entry point |
| --- | --- |
| Writing the choice to disk | `AppLocaleController.setLocale(...)` |
| Restoring it before the first frame | `AppLocaleController.restore()`, awaited in `bootstrap.dart` before `runApp()` |
| Where the value is stored | `LocaleStore` (default `SharedPreferencesLocaleStore`; assign `AppLocaleController.store` to change it) |
| Applying it to a *feature-scoped* slang instance | that feature's shell page `_syncLocale()` |

Any UI that changes the language (the Home → Settings tile, the login-screen
toggle, anything you add) must call its own feature-scoped
`LocaleSettings.setLocale(<Feature>Locale.x)` for the immediate rebuild **and**
route the app-wide change through `app_l10n.AppLocaleController.setLocale(...)`.
Calling `app_l10n.LocaleSettings.setLocale(...)` directly looks identical in the
running app but persists nothing, so the choice silently reverts on the next
cold start. See `shared/locale_core/README.md`.

## Key Commands

```bash
dart pub get                        # Resolve workspace dependencies
melos run build                     # Run build_runner for all packages
melos run build:app                 # Run build_runner for app only
melos run analyze                   # Static analysis on all packages
melos run format                    # Format all Dart files
melos run fix                       # Apply dart fix --apply
melos run test                      # Run tests with coverage
melos run changelog -- --version X  # CHANGELOG.md entry grouped by commit type (--package, --tag-pattern, --dry-run)
melos run deps:check                # Direct pins that drift or duplicate the barrels; then deps:align <pkg>, deps:diagnose after a pub get failure
melos run di:check                  # Injector regions and test harness match the archipelago: declarations
melos run build-prepare:debug       # Swap to debug dependencies
melos run build-prepare:production  # Production release: swap debug tooling and Marionette to noop
```

> **`shared/app_config/.env` is gitignored and auto-seeded.** `melos bootstrap`
> copies `.env.development` to `.env` if it's missing (via its `hooks.post`,
> see root `pubspec.yaml`) — this is what makes `melos run build` work right
> after a fresh clone with no manual `cp`. Switch flavors explicitly with
> `melos run env:switch -- <flavor>`.

> **`melos run build:app` is the fast inner loop, not a cold-start command.**
> It (and a bare `dart run build_runner build` inside `apps/`) only regenerates
> the *app's* own output. build_runner writes `build_to: source` output for the
> package it is invoked in and nothing else, so an app-scoped build can never
> produce a *dependency's* `lib/src/di/injector.module.dart` — the file that
> declares the `<Pkg>PackageModule` classes named in the app's
> `@InjectableInit(externalPackageModulesBefore: [...])`. Those files are
> committed for exactly this reason (see `.gitignore`); if you ever delete them
> — e.g. `melos run build:clean` — or add a new micro-package, run the full
> `melos run build` (which chains `build:select` then `build:app`) before the
> app-scoped one. Skipping that step surfaces as the unactionable
> `injectable_generator:injectable_config_builder on lib/di/injector.dart:
> FormatException: Not an instance of Type.`

> **Caution:** on Dart 3.13.0/Flutter 3.47.0, `dart fix --apply` (`melos run fix`)
> has confirmed-broken auto-fixes for `prefer_const_constructors_in_immutables`
> (mis-places `const` on primary-constructor classes, producing invalid syntax)
> and `unnecessary_null_checks` (strips a required `!` when surrounding types
> are unresolved) — both silent, with no error surfaced. Always review
> `git diff` after running it before committing; never run it unattended.

> **Note:** every slang `build.yaml` turns off `slang_build_runner` and
> turns on `slang_build_runner:legacy`. Do not switch it back. The default
> builder writes through a post-process builder (`build_to: source`), and
> build_runner 2.15+ throws `InvalidOutputException: Asset already exists`
> when such an output is on disk but not in the asset graph, for example
> after `.dart_tool/build` is deleted or restored from a CI cache.
> `--delete-conflicting-outputs` no longer exists to override it. The legacy
> builder overwrites existing files. In `build_runner watch` it generates
> once per process, so run `melos run l10n:generate:all` after editing
> translations.

## Environment Setup (cold start)

`.env`/`.env.<flavor>` under `shared/app_config` are gitignored (only
`.env.example` is committed), so a fresh clone or CI checkout has **none** of
them — only `env.dart`'s declared fields exist. Run, in order:

```bash
melos run env:init                    # scaffolds .env.<flavor> with placeholder values
melos run env:switch -- development   # copies .env.development -> .env
melos run build                       # regenerates env.g.dart (envied) + everything else
```

`env:init` scaffolds every flavor file with the **same non-empty placeholder
values** the generator wrote at project creation (`https://api.example.com`,
`replace-with-your-aes-key`, etc.) — not empty strings. `envied`
(`@EnviedField()`, no `defaultValue`) fails codegen outright on a genuinely
missing `.env` file, and treats a KEY absent from the environment map (never
seen by `env:switch`) the same way; a non-empty placeholder is what lets
`melos run build` succeed on a fresh clone with zero manual edits. Replace the
placeholders in `.env.<flavor>` with real values before shipping — they are
obviously fake and will not talk to a real backend.

Skipping `env:switch` (or running `melos run build` before it) is the one
sequencing mistake that still hard-fails: with no `.env` on disk at all,
envied's error is `Environment variable not found for field 'apiBaseUrl'`,
which reads like a code problem but is really "no active flavor selected
yet."

`shared/app_config/build.yaml` declares `.env` as an explicit build
`source`, so editing an already-scaffolded `.env` (e.g. via `env:switch` to a
different flavor, or hand-fixing a value) is picked up by the next `dart run
build_runner build`/`melos run build` — no `.dart_tool/build` cache surgery
needed for that specific case. If you ever *do* hit a build_runner run that
seems to replay a stale error despite the inputs looking correct (e.g. after
manually editing a `build.yaml`, or switching branches with different
generated-file state), `rm -rf **/.dart_tool/build` and rebuild — build_runner
is content-aware, so a wiped cache can only cost time, never produce wrong
output.

## Generated packages and upgrades

Packages that a brick generated (`features/...`, `infrastructure/...`, `devtools/scripts/...`) are fingerprinted in `.archipelago/generated/<brick>.json`, with the generated copy in `.archipelago/base/<brick>/`. Commit both with the packages. Running a brick again over changed packages stops with `Nothing was changed`; merge the newer version with `archipelago upgrade <brick>`, or overwrite with `ARCHIPELAGO_FORCE=1`. The `archipelago-upgrade` skill has the details.

## Agent skills

Task guides live in `.claude/skills/<name>/SKILL.md` and are indexed in `AGENTS.md` (Skills). Read the matching one before the task. Bricks you add later register theirs in that index.

## Conventions

- **Formatting**: Always use `dart format`
- **Commits**: Conventional commit style (`feat:`, `fix:`, `refactor:`, etc.)
- **Package naming**: `feature_api` + `feature_impl` for split packages; `feature_noop` for no-op variants
- **Barrel exports**: Every package has a barrel file at `lib/<package_name>.dart`
- **Dependency barrels**: a package never imports or declares equatable, injectable, get_it, meta, flutter_bloc, auto_route or slang directly. `*_api` contracts and pure-Dart packages depend on `shared/dependencies_core`; Flutter packages depend on `shared/dependencies`. Import the specific barrel per file (`equality.dart`, `di.dart`, `state.dart` (the chosen state-management package), `meta.dart`, `auto_route.dart`, `l10n.dart`); use the umbrella only in a file that needs three or more. Codegen tools (`build_runner`, `injectable_generator`, `auto_route_generator`, `slang_build_runner`) stay direct dev dependencies. A test that imports `di.dart` next to `flutter_test` writes `hide test` (injectable exports an annotation named `test`). The Archipelago repo checks this in CI
- **DI files**: `lib/src/di/injector.dart` (source) + `lib/src/di/injector.module.dart` (generated)

## Adding a New Feature

1. Create `features/<name>/` (`archipelago generate feature_monorepo_skeleton` scaffolds all of this)
2. Add a const `XManifest extends FeatureManifest` with `registerRoutes()`; the `_api` port is a plain interface with `launch()` (no `FeatureSDK`)
3. Implement the port in `XSDKImpl` with a plain constructor
4. Add a global module that calls `FeatureSDKRegistry.instance.register(const XManifest())` and `gh.lazySingleton<XSDK>(XSDKImpl.new)`. Use an eager `FeatureSDK` with `registerSingleton` only for a feature that must exist at boot
5. Declare the module in the feature's own `pubspec.yaml` under `archipelago: di_modules: [{class: XGlobalModule, depends_on: [...]}]` (`depends_on` lists packages whose GetIt types its `init()` reads eagerly), then run `dart run monorepo_toolkit generate host-registry`: it rewrites the `archipelago:feature_imports`/`feature_modules_before` regions of `apps/pico/lib/di/injector.dart`. `melos run di:check` fails when they are out of date
6. For local deps (repos, datasources, usecases), use the feature's `FeatureContainer` (`<name>_container.dart`) and forward each root type it needs in `<name>_imports.dart`. The shell page takes a lease in `initState`, builds after `lease.ready`, releases in `dispose`, and creates the Cubit/Bloc/Notifier from `_lease.get<T>()`; no `GetIt` outside `lib/src/di/`. `archipelago generate feature_monorepo_skeleton` scaffolds this shape
7. If the feature's DI init touches a platform channel, declare a test prerequisite. This covers a `@preResolve` that calls a plugin, an `init()` that eagerly resolves a plugin-backed type, and an eager constructor that does platform I/O. Add a `<Name>TestPrerequisite implements TestPrerequisite` (from `test_prereq`) in `lib/src/testing/` that fakes the call, export it from `lib/testing.dart`, and declare it under `archipelago: test_prerequisites: [{class: <Name>TestPrerequisite, reason: ...}]` in the package's `pubspec.yaml`. Then run `dart run monorepo_toolkit generate test-harness`. Without it, `apps/pico/test/di/injector_test.dart` fails with a `MissingPluginException`, and `melos run di:check` reports the harness as out of date
8. Nothing to add to the root `pubspec.yaml`: the root `pubspec.yaml` workspace globs `features/**` and `infrastructure/**`, so a new package needs only `resolution: workspace`
9. Add as dependency in app's `pubspec.yaml`
10. Run `dart pub get` and `melos run build`

For native Android and iOS code in a feature, set `isPlugin: true` when you run `archipelago generate feature_monorepo_skeleton`. The feature package (`<name>_impl` in an API/Impl split; `_api` stays pure Dart) gets `android/` (Kotlin `<Name>Plugin`), `ios/` (Swift `<Name>Plugin` and a podspec) and `lib/src/platform/<name>_platform_channel.dart`, which wraps one `MethodChannel` named `<domain>.<organization>/<package>`. Add a native call as a `case` in the Kotlin `when` and the Swift `switch`, plus a method on the Dart wrapper. The wrapper is injected into repositories like any datasource. It only calls the channel when a method runs, so it needs no test prerequisite.

## Adding Infrastructure

1. Create `infrastructure/<name>_api/` with vendor-agnostic contract (pure Dart, depends on `shared/dependencies_core`)
2. Create `infrastructure/<name>_impl/` with vendor implementation
3. Use `@InjectableInit.microPackage()` in `lib/src/di/injector.dart`
4. Export `PackageModule` class from barrel file
5. Declare the `PackageModule` under `archipelago: di_modules:` in the package's `pubspec.yaml` and run `dart run monorepo_toolkit generate host-registry`
6. If the package's DI init touches a platform channel (for example a `@preResolve` that calls `PackageInfo.fromPlatform()`), declare a test prerequisite as in step 7 of "Adding a New Feature", then run `dart run monorepo_toolkit generate test-harness`
7. Nothing to add to the root `pubspec.yaml`: the root `pubspec.yaml` workspace globs `features/**` and `infrastructure/**`, so a new package needs only `resolution: workspace`
8. Run `dart pub get` and `melos run build`
